### B. ReRoute Seoul에 대한 반론

**B1. 핵심 판단 근거인 ‘실내’ 필드가 데이터에 없다.** [사실+의견]
- 왜 문제: 대표 시연이 “우천 → 실내 대안”인데 MCP에는 실내 분류가 없다. 결국 LLM이 이름·설명으로 실내 여부를 *추론*해야 하고, 이는 “근거 없으면 확인 불가” 원칙과 정면 충돌한다. 원칙을 지키면 후보 대부분이 ‘실내 미확인’이 되어 시연이 빈약해진다.
- 필요한 증거: 실제 `attraction` 결과에서 설명문에 실내/실외를 판단할 단서가 몇 %나 있는지 샘플 20건 점검.
- 수정안: 시연 상황을 데이터가 받쳐주는 것으로 바꾼다. 예: “오늘 휴무인 곳 대체” → `운영시간` 텍스트의 **정기 휴무일** 파싱은 출처가 있다(임시휴무는 여전히 불가). 실내 여부는 ‘LLM 추정’ 배지로 명시 분리.

**B2. ‘복구(ReRoute/Recovery)’는 구현 범위 대비 과장이다.** [의견]
- 이동시간·실시간 운영정보가 없으면 남는 것은 “대체 장소 후보 + 정기 운영시간 + 지도 링크”다. 이는 동선 *재설계*가 아니라 **대체 후보 추천**이다. Track 1 공식 예시가 ‘길찾기·환승’을 함께 들고 있어 심사위원은 이동 연결을 기대할 것이다[추정].
- 증거: Kakao/ODsay/Google 경로 API의 외국어·대중교통 지원과 무료 한도 확인(미확인).
- 수정안: 이름·한 줄 소개를 “Plan B 찾기” 수준으로 낮추거나, 경로 API 1개를 확보한 경우에만 ‘동선’이라는 단어를 쓴다.

**B3. Track 1에서 범용 AI 컨시어지·ChatGPT와 구별이 약하다.** [의견]
- Track 1은 가장 붐빌 주제다(여행 챗봇은 가장 흔한 해커톤 아이디어)[추정]. “공식 출처·미확인 표시”는 신뢰 기능이라 **3분 시연에서 눈에 보이는 차이를 만들기 어렵다** — 범용 챗봇도 그럴듯한 대안을 말한다. 또 Track 1 평가 중점의 ‘멀티모달’, ‘외부 도구 연동’ 측면에서 ReRoute는 텍스트 + 데이터 1개로 얇다.
- 증거: 동일 질문을 범용 챗봇에 던졌을 때 실제로 틀린 운영정보를 내는 사례(공정한 재현 가능할 때만).
- 수정안: 차별점을 “운영시간 텍스트를 구조화해 *지금 시각 기준* 열림/정기휴무/미확인을 서버 규칙으로 판정”처럼 **눈에 보이는 계산**으로 만든다.

**B4. 인수 관점에서 외국인 대상 공개 서비스는 재단 부담이 크다.** [의견+추정]
- 본선 30점 ‘즉시 활용 가능’ 기준으로 보면, 재단이 인수해 관광객에게 열려면 LLM 운영비, 잘못된 안내에 대한 책임, 7개 언어 품질관리, 서드파티 MCP(나무기술 AI 운영) 의존이 생긴다. LLM 토큰비 자체는 작다(Luna 기준 Codex 계산 타당) — **문제는 비용보다 운영·책임 구조**다.
- 증거: 재단이 현재 Visit Seoul 챗봇 등 유사 서비스를 운영하는지(미확인), 인수 약정서의 유지보수 조항.
- 수정안: 인수 후 적용처를 “관광안내소 직원 보조 모드”로 명시해 리스크를 낮춘다.

**B5. 24시간·인원 대비 범위가 넓다.** [의견]
- 필수 3개 안에 실제로는: 대화형 누락정보 질문, MCP 연결(호출 방식 미확인), 운영시간 파싱, 실내 추론, 2안 비교, 선택·수정, 한/영 전환, 모바일 UI가 들어 있다. 3인이면 가능하나 **1인으로는 2안 비교·수정까지 어렵다**.
- 1인: Streamlit 1화면, MCP 검색+상세 1회, 대체 카드 1개 + 근거·미확인 배지. 2인: + 한/영, 정기휴무 판정. 3인: + 2안 비교·수정.

**B6. 설계가 팀 규모에 비해 무겁다.** [의견]
- FastAPI + Next.js 분리, JSON 계약, 도구 추상화 2개, 3인 교대 일정, 위험 10개 표 — 1~2인이면 Streamlit(또는 FastAPI 단일) 하나로 충분하다. 기획서 분량(약 250줄)도 국회 공모전이 주력인 상황에 비해 과하다. 신청서는 **7문항**이므로 기획 작업은 그 7문항 초안에 맞추는 것이 효율적이다.

**B7. MCP 의존이 가장 큰 단일 실패점인데 검증이 뒤로 밀려 있다.** [사실+미확인]
- PlayMCP 서버를 OpenAI Responses API나 자체 서버에서 직접 호출할 수 있는지, 카카오 계정 인증이 필요한지, 쿼터는 얼마인지 모른다. 행사 당일 처음 확인하면 19~21시를 통째로 잃을 수 있다.
- 수정안: **행사 전** MCP 클라이언트(예: 도구함 추가 후 Claude/ChatGPT 연결)로 3개 도구를 실제 호출해 응답 필드를 확인한다. 이는 데이터 탐색이지 핵심 기능 코드가 아니다[의견]. 대안 경로로 [Visit Seoul API](https://api.visitseoul.net/main/home?lang=ko) 키 신청도 미리 넣어 둔다(승인 소요 미확인).

### C. 대안 비교 (점수는 모두 **[추정/예측]**, 5점 만점)

- **A. ReRoute Seoul 축소판 (Track 1):** 휴무·우천으로 빠진 한 곳의 대체 후보 + 정기 운영시간 판정 + 근거·미확인 배지.
- **B. Visit Seoul 다국어 콘텐츠 점검 에이전트 (Track 2, 신규 제안):** MCP로 같은 콘텐츠를 7개 언어로 조회해 ① 번역판 누락(한국어 대체 발생) ② 언어별 운영시간·주소·연락처 불일치 ③ 운영시간 누락·형식 오류 ④ 동기화 지연(`get_sync_status`)을 찾아 **이슈 목록 + 수정 초안 + 언어별 커버리지 지표**로 보여주는 재단 실무자용 도구. 외국인이 겪는 “잘못된 정보” 문제를 데이터 원천에서 줄인다는 프레임.

### 2. 해석 — 세 후보의 문제 실재와 빈틈

**후보 1 「문제 이후 도움 연결」**
- 문제의 실재: **가장 강하다 [사실 기반]**. 공식 신고 데이터와 유형별 수치, 서울시가 공식적으로 밝힌 실패 원인이 있다.
- 다만 Codex 원안처럼 ‘상황을 말하면 공식 경로를 알려 준다’ 수준이면 **1330 채팅(24시간 다국어)과 겹친다 [의견]**.
- 빈틈은 **신고의 질**에 있다 [사실+의견]. 서울시가 직접 밝힌 실패 원인이 증거 부재, 운행기록 불일치, 연락 곤란이다. 접수 창구는 늘었지만(QR) 처분 가능한 신고로 이어지지 않는다(487건 중 8건).
- 또 조치 결과 1위가 ‘설명·안내’다. **오해에서 나온 신고**(할증·통행료 등 정상 요금)가 상당수일 가능성이 있다 [추정, 세부 비율 미확인].

**후보 2 「일정 변경(ReRoute)」**
- 문제 근거: **약하다**. ‘부족했던 정보 1위가 교통정보(16.1%)’ 정도이고, 일정이 틀어지는 빈도나 심각성을 보여 주는 공식 자료는 찾지 못했다.
- 기존 서비스와의 관계 [의견]: 재단이 이미 **추천·일정형 K-관광 AI 에이전트**를 운영 중일 수 있다(현재 운영 여부 미확인). 사실이라면 재단에 같은 계열 서비스를 인수하자고 설득하기 어렵다.

**후보 3 「다국어 정보 검수」**
- 문제 근거: **확인한 것이 없다**. 재단 담당자의 실제 업무 부담을 보여 주는 공개 자료를 찾지 못했다. 필요성을 입증하려면 재단 실무자에게 들어야 하는데, 그건 외부 연락이라 사용자 판단 사항이다.

### 3. 제안 — 후보 1을 좁힌 안 (가칭 「Fair Claim Seoul」, Track 1)

**한 문장:** 택시·쇼핑에서 요금 문제를 겪은 외국인이 자기 언어로 말하고 영수증을 찍으면, 다음을 돕는다.
1. **정상 요금 규칙인지 먼저 설명한다.** 심야·시계외 할증, 통행료 같은 공식 고시 기준만 쓴다.
2. 신고가 필요하면 **처분에 필요한 증거 체크리스트**(영수증, 차량번호, 승하차 시각·위치, 사진, 연락 수단)를 채우게 한다. 빠진 항목은 묻는다.
3. **알맞은 창구**(택시 QR·120, 관광공사 신고, 1372)와 **한국어+원어 신고문 초안**을 만든다. 제출은 사용자가 직접 한다.

**근거와 평가**
- 문제 실재 [사실]: 위 1-(1)·(2)의 공식 수치가 서류 ‘주제 이해도 30’의 근거가 된다.
- 빈틈 [사실+의견]: 접수 창구는 많은데 **처분 가능한 신고로 만드는 단계**를 돕는 도구는 찾지 못했다. 확인된 AI는 추천형이거나 상담원 보조형뿐이다.
- 기관 가치 [의견]: 근거 없는 신고는 줄이고(설명으로 해소) 근거 있는 신고는 처리 가능하게 만든다. 재단 Visit Seoul 앱이나 불편신고 안내 페이지에 모듈로 붙이는 형태를 상정한다.
  - 단, **신고 처리 주체는 서울시·관광협회·관광공사**다. 재단이 인수해 쓸 경로는 Visit Seoul 연계 수준이고, 기관 간 협업이 필요하다 [미확인].
- Track 1 적합 [사실]: 공식 불편사항 예시의 ‘교통·결제’에 해당한다. 평가 중점인 **멀티모달**(영수증 사진)과 대화형도 직접 충족한다.
- 24시간·1인 구현 [의견]: 비전 LLM과 구조화 출력, 고정 규칙표, 창구 매핑만 있으면 된다. **MCP나 외부 실시간 API에 의존하지 않는다.** 앞서 정한 PlayMCP 실호출 점검은 이 안에서는 필수가 아니다.
- 3분 시연 [의견]: “명동→홍대 택시 요금이 이상해요(일본어)” 입력 → 영수증 촬영 → 할증 설명 → 빠진 증거 질문 → 한·일 신고문과 창구 안내. 정서적으로 분명하고 보여 주기 쉽다.
- 보안·개인정보 15점 [의견]: 차량번호·사진·연락처를 다루므로 **서버에 저장하지 않고 신고문만 생성**하는 설계 자체가 심사 포인트가 된다.

**약점 (정직하게)**
- **AI가 부당요금을 판정하면 안 된다.** 이동거리와 경로 없이는 ‘과다 청구’를 판단할 수 없다. 할 수 있는 일은 규칙 설명과 증거 정리까지다. 이 선을 넘으면 법적·사실적 위험이 생긴다.
- **처분율이 낮은 진짜 원인이 증거인지, 근거 없는 신고가 많아서인지 비율을 모른다.** 서울시는 사유만 나열했다. 서비스 효과를 숫자로 약속하지 않는다.
- 신고 건수가 방문객 1,636만 명 대비 작다. 다만 ‘신고는 빙산의 일각’이라는 주장은 근거가 없어 쓰지 않는다.
- QR 도입 후 7개월간 서울 택시 외국인 신고 487건은 공사 연간 택시 신고 268건(전국)보다 많다. 이는 창구가 쉬워지면 신고가 늘어난다는 정황이지만, **집계 체계가 달라 직접 비교는 할 수 없다 [추정]**.
- 택시 요금 고시값(기본요금·할증률)과 각 창구의 접수 양식 항목은 **아직 1차 확인 전**이다. 수치를 박기 전에 서울시 고시로 확인한다.
- ‘ChatGPT에 물어보면 되지 않나’라는 질문에 대한 답은 **공식 창구 매핑, 처분 실패 사유에 맞춘 증거 체크리스트, 한국어 신고문 형식**이다. 이게 3분 안에 보이도록 해야 한다.

**검토했지만 뺀 대안**
- 결제·앱 접근 안내: 문제는 실재하지만 해법이 인프라(EMV, 여권 인증) 쪽이고, 2026년에 빠르게 바뀌고 있어 AI 안내의 가치가 줄어들고 있다.
- 숙박 분쟁(예약취소·위약금 28.1%): 국외 OTA와 관할이 얽혀 24시간 시연으로는 범위가 크다.
